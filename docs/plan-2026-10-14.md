## 1. Fix `DiskLoadHandler.wait()` dropping other loads' completions (0.21)

`diskio.py` (load side, `for r in self.get_finished()` in `wait`) drains
`get_finished()`, which empties `_ready`, and keeps only the ids it was asked
about. Any other load's completion is lost for good, since the job is already
popped. Same bug the store side already fixed. Load ids do reach `wait()` via
`reset_cache` (vLLM 0.21 `scheduler.py:850-855`), so it is rare. Ship with the
next restart; not worth one on its own.

## 2. Make the load copy wait on the compute stream (0.21, Xid candidate)

vLLM 0.31's `SingleDirectionOffloadingHandler.transfer_async` does
`stream.wait_stream(current_stream)` for loads too (`cpu/gpu_worker.py:690-696`):
with async scheduling, zeroing of a destination block shipped in an earlier
step is ordered against nothing else. 0.21's handler waits only for stores, and
`--async-scheduling` is on. Fits the 12:43 fault (both ranks, one load, no
burst, 0 overlaps). The copy stream is created inside upstream's handler, so
the wait needs a clean insertion point. Needs a restart: ask first. The ledger
says afterwards whether the Xids stop.

## 3. Measure whether GPU prompt-block protection still pays (no restart)

`protected_fraction` is hot. Lower it to its minimum for a period of normal
traffic and compare against 0.75: share of returning turns that hit on the
GPU, share restored from disk, and time to first token. Note `kvmgr_enabled=0`
does NOT measure this (it falls back to patch6's protection, not to none).
Whether 0 is an accepted value is unchecked. Run from the vllm-proxy session.

Reference points: warm GPU hit 0.9 s (2K delta on 770K); disk restore 11 s
(700K after restart); cold 430-795 s.

## 4. The 0.31 move (parked, nothing scheduled)

- **Disk tier:** port the spike branch. Left to do: check on the cluster which
  groups 0.31 offloads (`prefix_cacheable_group_ids` only) and the
  `offload_prompt_only=True` default (decode blocks no longer stored). The
  on-disk tier is orphaned either way (FileMapper fields and the GPU layout
  changed).
- **Disk direction:** keep our own spec. Upstream tiering uses one
  `/dev/shm` region per host, the fs tier writes from the scheduler's view of
  it, and worker rank is `device_index % world_size` (both nodes become rank 0
  with one GPU each). `simple_kv_offload`'s disk backend keeps its index in
  memory, so nothing survives a restart.
- **GPU manager:** drop it unless item 3 says otherwise. If rebuilt: a
  `FullAttentionManager` subclass installed by wrapping
  `single_type_kv_cache_manager.register_all_kvcache_specs` (run it, then
  replace the `MLAAttentionSpec` entry). Registering through the public call
  fails either way: early empties the "registry is empty" check so built-ins
  never register; late asserts on the conflict.
- **DSpark patches:** re-derive against 0.31's built-in DeepSeek V4/V4.1,
  `DSparkDraftModel` and `nvfp4_ds_mla` rather than rebase. The real cost of
  the move; some patches may simply go away.
- **Ledger:** `step_hits` reads V1's `input_batch.block_table`; 0.31's
  default V2 model runner needs its own reader (today it would report
  `in_step=None`, never 0).

Spike results: pristine gate has the 8 disk/journal/verify/ledger suites green
on 0.31; the GPU-manager suites stop at `harness.load()`. Effort guesses: disk
tier 1-2 days plus validation boots; GPU manager 0 (drop) to 1-2 weeks;
DSpark 1-3 weeks.

## 5. Restore throughput under load (next; v0.4.4 adds the poll arm)

Under heavy prefill an 858K restore took 166 s against 11 s idle (~20
blocks/s against ~280). The shape, read from `DiskLoadHandler._collect` and
0.21's `cpu/gpu_worker.py`:

- Completions are noticed in `get_finished`, once per scheduler step, and the
  next round is submitted in the same call. With `load_inflight_max=1` that is
  at most one round per step: `load_ops_max / refs[0]` blocks of group 0
  (2048 / 62 = 33; the DSpark flags file's 1024 makes it 16).
- Each round now waits for the compute queued at submit, which includes the
  step just enqueued. With async scheduling the copy may then finish after the
  next step's `get_finished`, so it can be one round per two steps.
- **Polling (v0.4.4, `load_poll_ms`, off by default).** I expected it to
  help less than the knobs below: a round submitted mid-step still waits for
  the forward already queued, so the best a poller saves is the async lag.
  The ask was to measure it, so it is built. The poll thread arms on the
  compute stream the last step captured, never its own current stream.
- `load_inflight_max` > 1: upstream chains rounds on one stream
  (`wait_event(last end_event)`), and each round's stream is armed, so N
  rounds run back to back after the forward. "4 killed the engine" was
  measured without the wait (see CLAUDE.md), so it is worth re-measuring.

Arms, one at a time, each gated on `kvrace.py run --arm on --loads 1000`
clean and a 700K restore about 10 s idle, then timed on a restore under
prefill:

1. Drop the flags file's `load_ops_max=1024` (the Xid experiment, now
   answered) back to the code default 2048.
2. `load_inflight_max` 2, then 4.
3. Only then `load_ops_max` above 2048 (still under `load_batch_max=192`
   blocks; group 0 at 4096 is 66 blocks).
4. `load_poll_ms` 2 (with the best of 1-3), then 1.

Read each arm from `/kv/workers` (load handler): the change in
`blocks_to_gpu / steps_loading` over one restore, `blocks_step_max`, and
`blocks_to_gpu_poll` for the poll's share. The ledger's `via` says which
thread submitted each load.

All hot, no restart. Run from the vllm-proxy session.

## 6. Borrowed from sparkcache: failed restore -> recompute, and checksums (v0.4.6)

Both off until the cluster has run them (vllm-proxy `ask1.md`).

- `disk_load_failure_recompute`: a failed restore becomes invalid blocks and
  a rolled-back request instead of upstream's assert. Needs
  `kv_load_failure_policy: "recompute"` in KV_TRANSFER_CONFIG to reschedule
  rather than fail the request. kvmgr fixes 0.21's single-group unpack in
  `_update_requests_with_invalid_blocks` (sparkcache patch 031 semantics).
  Unproven offline: that 0.21's KVOutputAggregator unions invalid blocks across
  the two ranks (0.31's does), so the gate must fail a load on the worker only.
- `disk_checksum_write` / `disk_checksum_verify`: CRC32 in an xattr. Unknown
  offline: whether `/kvoffload` keeps user xattrs inside the container, and the
  restore-time cost (zlib CRC32 on Grace).
- **Then the prize:** once a failed restore is proven survivable, the boot
  walk stops being mandatory. It exists only because a missing file is fatal.
  It could run in the background after the API opens (unverified keys answer
  as hits; a miss on disk becomes a recompute). Not built; it needs the gate
  result first.
